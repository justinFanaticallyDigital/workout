01

Strategy

Match the spec's reuse-first philosophy. Anchor on the four screens that define the new product, then ladder out.

Design priorities, in order

  • Anchor first. Design the Goal Pulse strip and Next Action card before anything else — they show up on every Gameplan tab state and define the visual vocabulary for trajectory, projection, and recommendation.
  • Picker before tab. A user can't see the Gameplan tab without first picking one. Designing the picker forces the question of "what is a Gameplan, visually?" — the answer cascades into the tab.
  • Planning Mode last in framework. It depends on every other surface having stable visual primitives (chart, target tile, handle) — designing it first means redesigning everything afterward.
  • Gameplans 4–8 are content, not design. Once 3 launch Gameplans verify the framework, the rest are seed data and copy.

What stays put (do not touch)

  • Logger · 4 skeletons explored, 1 to pick + polish per theme
  • Exercise library, history, body metrics, photos, injuries · all keep current chrome
  • Nutrition food diary · gets a thin "Plan vs actual" strip; otherwise unchanged
  • Stretch timer, custom activity forms · untouched
  • Theme system, the 7 themes, ft-* tokens · locked. Every new screen must read in all 7.

05

Dependencies & risks

What blocks what · what could derail · how I'd de-risk early.
Item Risk Why it's a risk Mitigation
Trajectory chart in 7 themes High Charts have to read in Iron, Lab, Notebook, Arcade, Blueprint, Cyberpunk, Graffiti — feasibility band + dual-line + dots is a lot of visual surface to keep coherent. Design the chart in Lab first (clinical baseline), then port. Keep band/line/dot semantics; let the theme own only stroke, fill, font.
Goal Pulse strip High Cross-screen primitive. If it changes after 8C, every check-in card and planning panel needs revisiting. Lock its contract during 8B. Treat the strip as the first deliverable; review with 3 goal types (body, lift, perf) populated.
Planning Mode information density High 9 handles + 3 live panels at 380px is a hard problem. The spec acknowledges "right-side panel or bottom sheet on narrow viewport." Two parallel directions in 8D: (1) tab-switched bottom sheet, (2) full-screen flow with sticky projection card. Compare side-by-side.
Picker setup variability Med Each Gameplan needs 3–5 different setup inputs (Lean Out asks target weight; First 90 Days doesn't). Setup screen can't be a single template. Design setup as a slot system: header, body slot (per-plan input form), footer. Validate with 3 launch plans before generalizing.
Single workout library scoping Med "Auto-derived list of every BlockDay across every shipped Gameplan" gets very long very fast. Filter UX matters. Design empty + 3-state (filtered, sparse, full). Consider grouping by Gameplan to give visual order.
Lifestyle log sheets Med Three input types (numeric, G/Y/R, 1–5) plus optional body-part picker for pain. Per-theme styling pressure. Design one shared sheet shell; vary only the input control. Pain check is the only outlier; treat it as a separate variant.
Recommendation card hierarchy Med Three severities × four action types = 12 visual states. Easy to over-design. Same chrome for all; use only color + iconography for severity. Action affordance always in the same slot.
7-theme contrast floor Med Spec §13 requires WCAG AA across all themes. New surfaces with charts and bands are particularly exposed. Run scripts/audit-theme-contrast.js after every color decision. Treat band fills + line strokes as new tokens, audit them.
Custom build re-shell Low Wrapping the existing Program Engine in Gameplan vocabulary — visual work mostly already done. Defer to 8G. Re-skin existing flows; don't redesign.
Migration banner / legacy disclosure Low Edge case for existing users. Easy to over-engineer. Single banner, single disclosure. Designed late (8G) once everything else is settled.
06

Open decisions before we start

Spec §12 lists 7. These are the design-side decisions I'd want answered before phase 8B begins.
D1
How many directions per anchor screen?
Picker, Gameplan tab, Planning Mode, Check-in card. Spec doesn't specify.
Recommend2–3 directions for each anchor, 1 direction elsewhere — focus exploration where it matters.
D2
Theme treatment for new surfaces
Logger has 7 theme variants. Should every new surface get all 7, or do we lock theme to logger only?
RecommendAll 7 themes, all surfaces — the spec calls this out in §13. Design in Lab first; port systematically.
D3
Where does Goal Pulse "detail" live?
Spec says "Tap → detail with chart." Sheet, drawer, or full route?
RecommendBottom sheet at 70% height — keeps tab context, reads as a peek.
D4
Planning Mode entry — sandboxed route or modal-over-tab?
Spec says "/gameplan/[id]/planning" but UX-wise a modal-over-tab might feel less destructive.
RecommendFull route, hide bottom nav (already in spec). Reinforces "this is a serious edit."
D5
Logger skeleton — pick now, or after Gameplan tab?
Currently 4 skeletons exist. Picking changes how "Today" / "Next Action" lands.
RecommendPick now. The Next Action card on the Gameplan tab links straight into the logger; we need a settled visual to hand off to.
D6
Check-in delivery — modal, full route, or just a card?
Spec leaves the surface format open.
RecommendCard on tab → expands to full-route detail. Card stays dismissable; detail gives recommendations real estate.
D7
Goal Pulse sort order
Multi-goal users — by priority? By projection-status (behind first)? By goal type?
RecommendBy priority field (already on the model), then by status. Off-track surfaces above on-track within priority.
